    Chapter 4

    Keyboards and buttons

    Telegram has two keyboards: the inline one attached to a message, and the reply one that replaces the user's keyboard. They are not interchangeable, and picking the wrong one is a design bug users feel immediately.

    Inline keyboards with the helpers

    Hermes ships tiny builders that read left-to-right the way the keyboard renders: 

    bot.Command("menu", func(c *hermes.Context) error {
    return c.Send("Pick one:", hermes.WithKeyboard(hermes.Keyboard(
        hermes.Row(
            hermes.Button("👍 Yes", "vote:yes"),
            hermes.Button("👎 No", "vote:no"),
        ),
        hermes.Row(
            hermes.Button("Open docs", "nav:docs"),
        ),
    )))
})

    Keyboard takes rows, Row takes buttons, Button takes a label and a callback-data string. Tap a button and Telegram sends you a callback_query carrying that string — which is why chapters 5 and 6 exist.

    The 64-byte rule

    Callback data is capped at 64 bytes of UTF-8, enforced by Telegram and checked by Hermes (the constant is exported as hermes.MaxCallbackDataBytes). A short prefix plus an id fits easily. A JSON blob of your entire form state does not. Store state server-side; put the key in the button.

    Building markups by hand

    When the helpers are too rigid (dynamic rows, URL buttons, disabled buttons), build the struct directly. It is an ordinary type: 

    markup := hermes.InlineKeyboardMarkup{
    InlineKeyboard: [][]hermes.InlineKeyboardButton{
        {
            {Text: "Read the post", URL: "https://example.com/post/42"},
        },
        {
            {Text: "Approve", CallbackData: "approve:42"},
            {Text: "Reject", CallbackData: "reject:42",
                Disabled: &hermes.DisabledButton{}}, // greyed out, untappable
        },
    },
}
return c.Send("Moderation queue item #42", hermes.WithKeyboard(markup))

    Disabled buttons and markup-level force-reply arrived in Bot API 10.3, and Hermes exposes them the day they're in the schema, with no wrapper lag. URL buttons never hit your bot at all; Telegram opens the link client-side. SwitchInlineQuery drops the user into inline mode in another chat (note it is a *string field, like several on this struct, so a two-line ptr helper earns its keep here). Both are free engagement. Use them.

    Reply keyboards: the other kind

    A reply keyboard replaces the user's own keyboard under the composer. Tapping a button sends its label as an ordinary text message. There is no callback, no data, just text you then match on: 

    markup := hermes.ReplyKeyboardMarkup{
    Keyboard: [][]hermes.KeyboardButton{
        {{Text: "📍 Send location", RequestLocation: true}},
        {{Text: "☰ Menu"}, {Text: "✕ Cancel"}},
    },
    ResizeKeyboard:   true,
    OneTimeKeyboard:   true,
}
return c.Send("Where are you?", hermes.WithMarkup(markup))

    Three flags matter more than the rest:

    • ResizeKeyboard: almost always set it. The default keyboard is comically tall on phones.
    • OneTimeKeyboard — collapses after one tap. Right for one-shot questions, wrong for persistent menus.
    • Selective — in groups, shows the keyboard only to the user you're replying to. Without it, everyone in the group gets their keyboard hijacked, and they will tell you about it.

    Removing a keyboard

    Users notice a stale reply keyboard and read it as a bug. Remove it with the typed client when the flow ends: 

    _, err := c.Bot.SendMessage(c.Context, hermes.SendMessageParams{
    ChatID:      chatID,
    Text:        "All done.",
    ReplyMarkup: hermes.ReplyKeyboardRemove{RemoveKeyboard: true},
})

    Editing keyboards after the fact

    The single most useful inline-keyboard pattern: swap the buttons after a tap so the choice can't be made twice. 

    bot.CallbackPrefix("vote:", func(c *hermes.Context) error {
    choice := strings.TrimPrefix(c.Data(), "vote:")
    if err := recordVote(c, choice); err != nil {
        return err
    }
    // Replace the keyboard with nothing. The vote is final.
    if err := c.EditKeyboard(nil); err != nil {
        return err
    }
    return c.Answer("Vote recorded.")
})

    Notice the order: record first, edit second, answer last. If recordVote fails, the buttons stay in place and the user can try again. Reorder those three lines and you have a vote that disappears without being counted.
