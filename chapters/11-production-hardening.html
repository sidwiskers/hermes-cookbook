    Chapter 11

    Production hardening

    A bot that works on your laptop fails in production in four predictable ways: floods, duplicates, silent errors, and blindness. Hermes ships a package for each. This chapter is the pre-flight checklist.

    Rate limiting: the flood gate

    Telegram rate-limits you, and abusive users will too. The ratelimit package is a sharded, bounded token bucket installed as middleware: 

    limiter, err := ratelimit.New(5, time.Minute, // 5 updates a minute…
    ratelimit.WithBurst(2),                  // …with a small burst allowance
    ratelimit.WithKey(ratelimit.ByUser),     // …counted per user
    ratelimit.WithMaxKeys(100_000),          // …and a cap on tracked users
    ratelimit.WithRejected(func(c *hermes.Context, d ratelimit.Decision) error {
        return c.Ephemeral("Slow down a little.")
    }),
)
if err != nil {
    log.Fatal(err)
}
bot.Use(limiter.Middleware())

    Rejected updates surface ratelimit.LimitError (wrapping ratelimit.ErrLimited) unless you handle them yourself in WithRejected, which you should: a silent drop looks like a broken bot, while a one-line ephemeral notice looks like a policy. Idle buckets expire (WithIdleTTL), and MaxKeys means a flood from millions of distinct fake users cannot grow the limiter without bound.

    Deduplication: make side effects retry-safe

    Duplicate delivery is possible, but the exact retry behaviour depends on how updates enter your bot. A queued webhook returns success once the update is admitted, before the asynchronous handler finishes; polling advances its offset as accepted updates are dispatched. Synchronous webhook replies can return an error so Telegram retries, and an overloaded webhook deliberately answers 503 with Retry-After. Network failures can also make delivery ambiguous. If a handler charges a card or posts to a channel, make the side effect safe to see twice. dedupe claims each update atomically before your handler runs: 

    dedup := dedupe.New(myStore, // implements dedupe.Store
    dedupe.WithTTL(24*time.Hour),
    dedupe.WithDuplicate(func(c *hermes.Context) error {
        return nil // already handled; consume silently
    }),
)
bot.Use(dedup.Middleware())

    The store interface is deliberately tiny so it can sit on Redis, Postgres, or the bundled in-memory implementation for single-process bots. Put the middleware before anything expensive. A downstream error releases the claim, which is especially useful for retryable synchronous webhook flows. The goal is not to pretend every transport retries every handler error; it is to make duplicate delivery harmless wherever it can occur.

    Errors: three kinds, three responses

    Hermes distinguishes API errors (Telegram said no), transport errors (the network said nothing), and handler errors (your code said ouch). The practical setup: 

    bot.SetErrorHandler(func(c *hermes.Context, err error) {
    var panicErr *hermes.PanicError
    var limitErr *ratelimit.LimitError
    switch {
    case errors.As(err, &panicErr):
        alerts.Send(fmt.Sprintf("PANIC in handler: %v\n%s",
            panicErr.Value, panicErr.Stack))
    case errors.As(err, &limitErr):
        // expected; metrics only
    default:
        log.Printf("handler error: %v", err)
    }
})

    Panics carry their stack (Recover() saw to that), so the alert you get at 3 a.m. contains the line number, not a shrug. Rate-limit rejections are policy, not failure. Count them, don't page on them. Everything else is at least a log line.

    Observability: know before users tell you

    The observe package gives you handler lifecycle hooks and a lock-free metrics aggregator with fixed cardinality — counters you can safely scrape forever: 

    metrics := &observe.Metrics{} // the zero value is ready to use
bot.Use(observe.Middleware(metrics))

// anywhere, e.g. your /healthz handler:
snap := metrics.Snapshot()
log.Printf("updates=%d failed=%d avg=%s peak-in-flight=%d",
    snap.UpdatesSucceeded, snap.UpdatesFailed,
    snap.AverageUpdateDuration().Round(time.Millisecond),
    snap.UpdatesPeakInFlight)

    "Fixed cardinality" deserves emphasis: the metrics are aggregate counters and durations, not per-user or per-chat labels. You cannot accidentally create ten million time series by labeling with a chat id. The API simply doesn't let you. For outbound API calls, the matching WithAPIObserver option on the bot reports every Bot API call's lifecycle, including retries and rate-limit waits — and the same Metrics value implements that observer too, so hermes.WithAPIObserver(metrics) covers the outbound side with one line.
