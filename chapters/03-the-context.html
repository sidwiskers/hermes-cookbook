    Chapter 3

    The context

    Every handler receives one argument: *hermes.Context. It is the update, the chat, the sender, the API client, and the cancellation signal, rolled into one object. Learning it well is most of learning Hermes.

    Reading the update

    The context answers the questions you ask first in every handler: 

    bot.On(hermes.TextMessage, func(c *hermes.Context) error {
    text := c.Text()       // message text or caption
    user := c.Sender()     // *User; nil if the update has no sender
    id, ok := c.ChatID()   // the safe way to get a chat id
    _ = text
    _ = user
    _ = id
    _ = ok
    return nil
})

    The naming is deliberate: methods that can fail to produce a value return (value, bool) instead of nil-pointer landmines. c.ChatID() is the one you will call most. Almost every API method needs a chat id, and this is the safe way to get it.

    Command handlers get two helpers that save you the strings.Fields dance: 

    bot.Command("remind", func(c *hermes.Context) error {
    args := c.Argv() // ["10m", "stretch"] for /remind 10m stretch
    if len(args) < 2 {
        return c.Reply("Usage: /remind <when> <what>")
    }
    return schedule(args[0], strings.Join(args[1:], " "))
})

    Sending: the method families

    Context send methods come in pairs, and the pairing is consistent across the whole surface:

    • c.Send(text) → c.SendMessage(text)
    • c.Reply(text) → c.ReplyMessage(text)
    • c.Photo(f, cap) → c.PhotoMessage(f, cap)
    • c.Ephemeral(t) → c.EphemeralMessage(t)

    The short form returns only error. The Message-suffixed form returns the sent (*Message, error) — which you need the moment you want to edit, pin, or delete that message later. My habit: use the short form until the day you need the message id, then switch. Don't carry the extra return value "just in case". 

    msg, err := c.SendMessage("Working on it.")
if err != nil {
    return err
}

// do the slow thing, then edit the message we just sent
_, err = c.Bot.EditMessageText(c.Context, hermes.EditMessageTextParams{
    ChatID:    msg.Chat.ID,
    MessageID: msg.MessageID,
    Text:      "Done.",
})
return err
    What c.Edit edits

    c.Edit(...) edits the message represented by the current update. If you sent a new message and want to edit that one later, keep its returned *Message and use its chat and message ids as above.

    Send options, one at a time

    Every send method takes variadic hermes.SendOption. The common ones: 

    c.Send("<b>bold</b> and <i>italic</i>", hermes.HTML)
c.Send("_italic_", hermes.Markdown)
c.Send("silent update", hermes.Silent)
c.Send("no forwarding this", hermes.Protected)
c.Send("check https://example.com", hermes.NoPreview)
c.Send("spoiler", hermes.Spoiler)
    HTML is the only parse mode I trust

    MarkdownV2 requires escaping sixteen different characters and will reject your message at 3 a.m. because a user pasted a .. HTML needs three escapes (&, <, >) and fails loudly at the call site. Pick HTML, write a tiny escape() helper, move on with your life.

    Callbacks are answers waiting to happen

    When a user taps an inline button, Telegram shows a spinning indicator until your bot calls answerCallbackQuery. The context makes it one call: 

    bot.CallbackPrefix("vote:", func(c *hermes.Context) error {
    // c.Data() is the callback data string
    return c.Answer("Counted.")     // transient toast
})

bot.Callback("destructive:confirm", func(c *hermes.Context) error {
    return c.Alert("This cannot be undone.") // modal dialog
})

    If your handler does its work and has nothing to say, call c.Acknowledge() — an empty answer that just stops the spinner. Leaving the spinner running is the most common "the bot feels broken" bug in Telegram land, and it is always this.

    Chat actions, reactions, pins

    c.ChatAction("typing") // show the "typing…" bubble
c.React(hermes.ReactionType{ /* 👍 */ })
c.Pin()   // pin the incoming message
c.Unpin() // unpin it
c.Delete()

    None of these are exotic. But having them on the context, named after what they do, is what keeps handlers readable six months later.

    Cancellation and deadlines

    The context carries a real context.Context. Middleware such as hermes.Timeout can derive a deadline from it, and custom integrations may supply cancellation of their own. Pass it to everything that can block: 

    bot.Command("lookup", func(c *hermes.Context) error {
    row, err := db.QueryContext(c.Context,
        "SELECT note FROM notes WHERE id = $1", c.Args())
    if err != nil {
        return err // includes deadline/cancellation errors when this context ends
    }
    _ = row
    return c.Send("found it")
})

    One subtle but important detail: normal Hermes polling and queued webhooks stop accepting new updates on shutdown, then drain handlers that were already accepted. They do not cancel those handlers just because shutdown began. If a blocking operation needs a hard bound, install Timeout or give that operation its own deadline.

    Escape hatches

    The context covers the common cases. When you need something it doesn't wrap, the typed API client is right there: c.Bot is the embedded client behind every call, and the root facade re-exports all 185 method param types. You never have to leave your handler to make an unusual call.
