    Chapter 13

    Running a fleet

    One process, many bots. The fleet package hosts several independent Hermes bots under one lifecycle — shared plumbing, isolated failures, graceful shutdown for all.

    Why a fleet and not many processes

    Side projects multiply: a personal assistant bot, a channel cross- poster, the family's birthday bot. Running each as its own process means N binaries, N supervisors, N health checks. A fleet means one binary, one systemd unit, one graceful stop that drains every bot's handlers together. Bots stay fully independent (separate tokens, routers, middleware, sessions, rate limiters) but share the lifecycle and, if you want, the HTTP client.

    The smallest fleet

    main.gohost := fleet.New(fleet.WithBotMaxConcurrentUpdates(32))

alerts := host.NewBot(os.Getenv("ALERTS_BOT_TOKEN"))
alerts.Command("start", func(c *hermes.Context) error {
    return c.Send("Alerts bot is ready.")
})

support := host.NewBot(os.Getenv("SUPPORT_BOT_TOKEN"))
support.Command("start", func(c *hermes.Context) error {
    return c.Send("Support bot is ready.")
})

if err := host.Mount("alerts", alerts); err != nil {
    log.Fatal(err)
}
if err := host.Mount("support", support); err != nil {
    log.Fatal(err)
}
log.Fatal(host.Run(ctx))

    Each NewBot is a full *hermes.Bot. Everything from the previous twelve chapters applies unchanged. Mount gives it a name (used in status and failure reporting) and declares how it receives updates. Mounted with no options, as above, a bot polls with defaults.

    Mixed delivery: some poll, some serve webhooks

    Mount options pick the delivery mode per bot. Webhook bots share one HTTP server on exact paths: 

    host := fleet.New(
    fleet.WithWebhookAddress(":8443"),
)

host.Mount("alerts", alerts,
    fleet.WithPolling(hermes.PollOptions{Timeout: 30}))
host.Mount("support", support,
    fleet.WithWebhook("/hooks/support", hermes.WebhookOptions{Secret: s1}))
host.Mount("admin", admin,
    fleet.WithWebhookReplies("/hooks/admin", hermes.WebhookOptions{Secret: s2}))

    Two bots on webhooks and one on polling share a process without sharing anything else. Each webhook bot still wants its own secret. The per-path routing is not a substitute for per-bot authentication.

    Failure policy: isolate or fail fast

    When one bot's token is wrong or its update source dies at startup, what should happen to the others? You decide once, at construction: 

    host := fleet.New(
    fleet.WithFailurePolicy(fleet.IsolateFailures), // default: the rest carry on
    fleet.WithErrorHandler(func(f *fleet.Failure) {
        alerts.Send(fmt.Sprintf("bot %s failed: %v", f.Bot, f.Err))
    }),
)

    Isolation is the default and usually right for side-project fleets: the birthday bot being down shouldn't silence the alerts bot. Choose fail-fast when the bots are one logical service, shards of the same product, where running half of them is worse than running none.

    Status and shutdown

    for _, s := range host.Status() {
    log.Printf("bot=%s state=%s mode=%s", s.Name, s.State, s.Mode)
}

    Status is stable enough to drive a health endpoint. Shutdown is the same story as a single bot: cancel the context and the fleet stops intake on every bot, then drains in-flight handlers before Run returns. One Ctrl-C, cleanly handled, for the whole stable.

    Fleet rules of thumb

    • Name mounts after their function ("alerts", "support"), not their token or environment. Failure reports will read like prose.
    • Give every fleet an error handler. Isolated failures are silent without one. Isolation keeps the process up, but you still want to know.
    • Bound each bot with WithBotMaxConcurrentUpdates so one busy bot can't starve the rest of the process.
    • Test each bot with Hermes Lab (chapter 12) before mounting it. Fleets make operations easier, not broken bots healthier.
