    Chapter 12

    Testing with Hermes Lab

    Testing a bot against the real Telegram means a real token, a real chat, and a real mess. Hermes Lab is a deterministic in-process Telegram: virtual users, a virtual Bot API, and expectations you can assert on. Tests run in milliseconds and fail with readable diffs.

    Your first lab test

    A lab owns a fully-wired bot. You register routes on it exactly as in production, then deliver updates through virtual users: 

    bot_test.gofunc TestStartCommand(t *testing.T) {
    lab := testkit.NewLab(t)
    registerRoutes(lab.Bot) // the same function main() calls

    alice := lab.PrivateUser(1001, "alice")

    alice.Command("start").
        Want(testkit.Sent("Welcome, alice."))
}

    Read the test top to bottom: it says what it does, in the order it does it. No mocks of HTTP, no canned JSON files, no network. The update went through the real bot, router, and middleware; the Lab deliberately drives Bot.Handle synchronously instead of the production polling/webhook dispatcher. Only the wire is virtual.

    Actors and chats

    alice := lab.PrivateUser(1001, "alice")       // DMs
bob := lab.GroupUser(-400123, 2002, "bob")    // speaks inside a supergroup

alice.Command("profile")
bob.Text("is the bot here?")
bob.Callback("menu:open") // presses a button on the bot's latest message

    Each actor carries a stable user and chat identity, so session-keyed tests (chapter 7) behave exactly as in production: two users in one group get independent sessions, one user in two chats does too. CallbackOn targets a specific earlier message when the "latest" default isn't the one you want.

    Expectations

    Assertions read like the behaviour they check: 

    step.Want(testkit.Called("sendMessage"))
step.Want(testkit.Sent("order confirmed"))
step.Want(testkit.Edited("order confirmed ✅"))
step.Want(testkit.Answered("Saved."))
step.Want(testkit.Acknowledged()) // answered with no toast
step.Want(testkit.Deleted())
step.Want(testkit.NoCalls())      // handler stayed silent
step.Want(testkit.Matching("sendMessage",
    func(r testkit.Request) bool {
        return r.JSON["disable_notification"] == true
    }))

    Every Want returns the step, so assertions chain — and for error paths there are WantError and WantAPIError(code). When an expectation fails, the message tells you what the bot actually did — the observed method list — instead of a bare "expectation failed". Failed bot tests should read like bug reports, and these do.

    Failure is a feature

    The lab's best trick is planned failure. Your bot will eventually face rate limits, Telegram-side errors, and dropped connections; better to meet them in CI: 

    lab.API.RateLimitNext("sendMessage", 3*time.Second)
step := alice.Command("digest")
// assert the handler degraded gracefully instead of dying

lab.API.FailNext("sendMessage", 400, "message text is empty", nil)
lab.API.TransportErrorNext("sendMessage", errors.New("connection reset"))
lab.API.RespondNext("getMe", customBotUser) // exact response override

    Each Next affects exactly one upcoming call of that method. The lab stays deterministic by construction, never by timing.

    Replay: deduplication's test harness

    Duplicate delivery can happen (chapter 11). The lab makes replaying the exact same update a one-liner: 

    first := alice.Command("pay").Want(testkit.Called("sendInvoice"))
first.Replay().Want(testkit.NoCalls()) // same update id: dedupe swallows it

    If that second expectation ever fails, your dedupe middleware has a hole, found in a unit test instead of a payment dispute.

    FSM flows, end to end

    alice.Command("signup")
alice.Text("Ada").Want(testkit.Sent("Nice to meet you, Ada"))
alice.Text("London").Want(testkit.Sent("All done, Ada from London."))

    Conversations are just sequences of actor calls. This is where the lab pays for itself most: state machines have more paths than any human will click through, and each path is three lines of test.

    House rules

    • Register routes through the same function production uses. If the test wires its own routes, it tests a bot that doesn't exist.
    • Call lab.Reset() between scenarios sharing one lab, or make a lab per test. Reset clears retained messages, queued failures, and the request log.
    • Assert the user-visible surface — what was sent, edited, answered — before asserting which methods were called. Text first, plumbing second.
    • Keep the lab out of production builds by simply not importing testkit outside _test.go. That is the whole isolation mechanism, and it's enough.
