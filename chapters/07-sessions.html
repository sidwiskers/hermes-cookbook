    Chapter 7

    Sessions

    Bots are stateless between updates unless you make them otherwise. Hermes sessions are typed, keyed per user or chat, and installed as ordinary middleware. Nothing global, nothing hidden.

    The shape of it

    A session has three parts: a store (where values live), a key function (which updates share a value), and the manager that ties them together as middleware: 

    type prefs struct {
    Language string
    Timezone string
}

store := session.NewMemory[prefs](24 * time.Hour)
sessions := session.New(store, session.ByChatUser,
    session.WithNamespace("prefs"),
)

bot.Use(sessions.Middleware())

    NewMemory[T](ttl) is a sharded, lazily-expiring in-process store. Values disappear after the TTL. It is unbounded by default, which is convenient for small trusted workloads. If the number of session keys can be driven by untrusted traffic, set an explicit capacity instead: 

    store := session.NewMemoryWithConfig[prefs](session.MemoryConfig{
    TTL:        24 * time.Hour,
    MaxEntries: 100_000,
})

    At the configured limit, new keys return session.ErrCapacity instead of growing memory without bound. Existing keys can still be updated normally.

    Choosing the key

    Key functionOne session per…Right for
    session.ByUserTelegram user, across all chatsGlobal preferences, rate-limit state, wallets
    session.ByChatChatGroup settings, shared game state
    session.ByChatUserUser within a chatMulti-step forms, per-group profiles

    The default mistake is ByUser for everything. If a user starts a setup flow in your support group while another one is halfway through in DMs, ByUser mashes them together. When in doubt, ByChatUser is the honest default for conversational flows. Updates that carry no user or chat simply skip session attachment — the key function returns (Key{}, false) and the handler runs sessionless.

    Namespaces: two managers, one chat

    Namespaces let independent session managers coexist without key collisions — a preferences session and a game-state session can both key on ByChatUser and never see each other's values: 

    prefs := session.New(prefsStore, session.ByChatUser,
    session.WithNamespace("prefs"))
game := session.New(gameStore, session.ByChatUser,
    session.WithNamespace("game"))

bot.Use(prefs.Middleware(), game.Middleware())

    When memory is not enough

    The built-in store dies with the process. For anything that must survive a deploy, implement session.Store[T] (three methods: Load/Save/Delete, all context-aware) over Redis, Postgres, or whatever you already run. The contract is small on purpose: stores must be safe for concurrent use, and the manager handles serialization of updates within a key so two rapid-fire messages from the same user don't interleave read-modify-write cycles.

    Serialization, precisely

    The manager serializes updates that share a session key, not the whole bot. Two users' updates still run concurrently; two updates from the same user in the same chat queue up. That's the ordering you want for forms and counters, without paying for a global lock.

    Housekeeping

    In-memory stores expire entries lazily (on access) and expose Sweep() for the eager path. If you want expiry to be prompt rather than eventual, run the cleanup loop next to the bot: 

    go func() {
    if err := store.Cleanup(ctx, 5*time.Minute); err != nil {
        log.Printf("session cleanup stopped: %v", err)
    }
}()

    Cleanup blocks until the context ends and spawns no hidden goroutines of its own. You see it, you own it, you shut it down. Same philosophy as the rest of Hermes.

    One last rule, learned the hard way: keep session values small and boring. Ids, counters, a few strings. The moment a session holds a megabyte of deserialized API responses, you've built a cache with none of the tooling of a cache. Store the id, refetch the thing.
