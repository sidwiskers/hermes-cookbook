    Polling and webhooks

    Telegram can hand you updates two ways: your bot asks for them (polling), or Telegram POSTs them to you (webhooks). Hermes does both properly, and the choice matters less than people think.

    Polling: the default that keeps working

    bot.Run(ctx) polls. You have already seen it. When you want control, use bot.Poll with explicit options: 

    err := bot.Poll(ctx, hermes.PollOptions{
    Limit:      50,                 // clamped to Telegram's max of 100
    Timeout:    30,                 // seconds Telegram holds the long poll
    MinBackoff: 500 * time.Millisecond,
    MaxBackoff: 4 * time.Second,
})

    Zero values are deliberately sensible: limit 100, timeout 50 seconds, backoff from 250 ms to 8 s. Polling works behind NAT, on a laptop, on a free-tier VM with no domain name. It is also the only choice when Telegram cannot reach you at all.

    Cutting noise at the edge

    If your bot only cares about messages and callbacks, tell Telegram not to send you the rest: 

    err := bot.Poll(ctx, hermes.PollOptions{
    AllowedUpdates: []string{"message", "callback_query"},
})

    This is the single most effective "optimisation" most bots can make: the filtering happens on Telegram's side, before anything crosses the network.

    Webhooks: when push beats pull

    With webhooks, Telegram POSTs each update to your HTTPS endpoint. You need a public URL, and you need to tell Telegram where it is: 

    main.goconst path = "/telegram"

if err := bot.SetWebhook(ctx, hermes.SetWebhookParams{
    URL:         "https://bots.example.com" + path,
    SecretToken: secret,
}); err != nil {
    log.Fatal(err)
}

err := bot.ServeWebhook(ctx, ":8080", path, hermes.WebhookOptions{
    Secret: secret,
})

    Three things in that snippet are doing quiet, important work:

    • The secret token is compared against the X-Telegram-Bot-Api-Secret-Token header on every request. Requests without it are rejected. Set it — a webhook without a secret is an open relay into your handlers.
    • Request bodies are bounded at 8 MiB by default (MaxBodyBytes), so a malformed or hostile POST cannot exhaust memory before JSON decoding even starts.
    • Under overload — when every update slot in the dispatcher is busy — the server answers 503 with Retry-After. Telegram understands that response and redelivers. Your bot slows down instead of falling over.
    TLS stops before Hermes

    ServeWebhook expects a reverse proxy (nginx, Caddy, a load balancer) to terminate TLS. Telegram requires HTTPS on the public URL; Hermes itself speaks plain HTTP on your private port. That split is deliberate, not a missing feature.

    Replying in the webhook response

    Telegram lets a webhook answer an update in the HTTP response body, saving a whole API round trip. Hermes supports it with a second server mode: 

    err := bot.ServeWebhookReplies(ctx, ":8080", path, hermes.WebhookOptions{
    Secret: secret,
})

// inside a handler:
bot.Command("ping", func(c *hermes.Context) error {
    return c.RespondWebhook("sendMessage", map[string]any{
        "chat_id": mustChatID(c),
        "text":    "pong",
    })
})

    The trade-off is real: the handler runs synchronously inside the HTTP request, so a slow handler is now blocking Telegram's delivery. Use it for bots whose handlers are uniformly fast: lookups, cached answers, simple commands. Do not use it for bots that call external APIs in the hot path. For everything else the ordinary queued mode (ServeWebhook) is the right default.

    Mounting inside an existing server

    Already have an HTTP server? Skip ServeWebhook entirely and take just the handler: 

    mux := http.NewServeMux()
mux.Handle("/telegram", bot.WebhookHandler(hermes.WebhookOptions{
    Secret: secret,
}))
log.Fatal(http.ListenAndServe(":8080", mux))

    Same authentication, same body limits, same 503-under-load behaviour: your server, your middleware, your lifecycle.

    So which one?

    SituationUse
    Development, laptops, no public URLPolling
    Small-to-medium bot, one VMPolling (seriously)
    High volume, latency-sensitiveWebhook
    Serverless / scale-to-zeroWebhook (it's the only option)
    Handlers are all fast and pureWebhook replies
    Behind a corporate NAT you don't controlPolling

    My rule of thumb: start on polling, and only move to webhooks when you can name the concrete reason: volume, latency, or a platform that requires them. "Webhooks feel more professional" is not a reason; they add a public endpoint, a secret, and a TLS stack to your operational life.
