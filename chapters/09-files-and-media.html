    Chapter 9

    Files and media

    Sending a photo is one method call. Sending a hundred-megabyte video without loading it into memory, showing a typing-style progress hint, and surviving a flaky network takes a little more.

    Sending media

    The context exposes one method per media kind, each in the familiar short / Message-suffixed pair: 

    c.Photo(file, "a cat", hermes.Spoiler)
c.Document(file, "quarterly report", hermes.Protected)
c.Video(file, "launch trailer", hermes.CaptionAbove, hermes.Streaming)
c.Voice(file, "", hermes.Silent)
c.Sticker(file)
c.Animation(file, "loop")

    The file argument is Hermes's Upload type — it accepts a Telegram file id (for re-sending something Telegram already hosts), a public URL, or local content to upload. The third case is the one that matters for performance: uploads are streamed, not buffered. A 500 MB video costs the process a few small buffers, not 500 MB of heap. If you have ever watched a bot get OOM-killed because it read a whole file into a []byte "temporarily", you know why this is in the design principles and not the changelog footnotes.

    Media-group albums

    Albums go through the typed client with MediaGroupItem entries: 

    items := []hermes.MediaGroupItem{
    photoItem(upload1, "first"),
    photoItem(upload2, "second"),
    videoItem(upload3, "third"),
}
msgs, err := c.Bot.SendMediaGroup(c.Context, hermes.SendMediaGroupParams{
    ChatID: chatID,
    Media:  items,
})

    Two album rules Telegram enforces and your code should respect: 2–10 items, and captions on individual items only (there is no album-level caption). Order is preserved. If you need the album to land as one notification, send it with Silent off and resist the urge to also send a separate "here are the photos!" message. The album is the message.

    Keep users informed with chat actions

    Uploads are slow by nature. Telegram shows "sending photo…", "uploading document…" and friends when you ask: 

    if err := c.ChatAction("upload_document"); err != nil {
    return err
}
return c.Document(bigFile, "the report")

    Chat actions expire after about five seconds or when a message arrives, whichever comes first. For genuinely long uploads, re-send the action every few seconds from a ticker that stops when the upload returns. Users forgive a slow bot that looks busy; they abandon a slow bot that looks dead.

    Receiving files

    Incoming media arrives with a file_id on the message. The flow is always the same: getFile to learn the path, then download from Telegram's file endpoint: 

    bot.On(hermes.DocumentMessage, func(c *hermes.Context) error {
    doc := c.Message.Document
    f, err := c.Bot.GetFile(c.Context, hermes.GetFileParams{FileID: doc.FileID})
    if err != nil {
        return err
    }
    // f.FilePath is the path to fetch from the file endpoint.
    return ingest(c.Context, f.FilePath)
})

    Filter first (hermes.DocumentMessage, hermes.PhotoMessage, …) and the handler can assume the media is there. That's what the filters are for. Photos arrive as an array of sizes; the last element is the largest. Bots that need originals should ask users to send the image as a document. Telegram recompresses photos, and no bot API setting changes that.

    Editing media

    Text edits (c.Edit) and caption edits (c.EditCaption) cover most needs. Swapping the media itself goes through EditMessageMedia with an InputMedia value — and yes, uploaded replacement media streams too, including for ephemeral messages (chapter 10), which arrived with Bot API 10.3.

    A word on file ids

    File ids are stable per bot and free to re-send — uploading the same asset twice is wasted bandwidth. Cache the id Telegram returns in the sent Message the first time, and re-use it forever after. This one habit turns a media-heavy bot from bandwidth-bound to instant.
