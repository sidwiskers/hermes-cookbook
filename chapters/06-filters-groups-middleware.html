    Chapter 6

    Filters, groups, middleware

    Exact commands and exact callbacks only get you so far. The rest of routing is three ideas: filters that match updates, groups that share filters, and middleware that wraps handlers.

    Dispatch order, precisely

    For every update, Hermes tries, in order:

    1. exact command match (bot.Command),
    2. exact callback-data match (bot.Callback),
    3. callback prefixes, longest first (bot.CallbackPrefix),
    4. filtered routes in registration order (bot.On),
    5. the fallback (bot.OnUpdate).

    At most one handler runs. "Longest prefix wins" is the rule that saves you: "admin:user:" beats "admin:" no matter which you registered first.

    Filters are functions

    A filter is func(*Context) bool — no interface, no registration, no magic. Hermes ships the obvious set: 

    bot.On(hermes.PhotoMessage, handlePhoto)
bot.On(hermes.PrivateChat, handleDM)
bot.On(hermes.FromUsers(adminID), handleAdmin)
bot.On(hermes.InChats(supportChatID), handleSupport)
bot.On(hermes.TextEquals("yes", "y", "YES"), handleYes)
bot.On(hermes.TextPrefix("remember "), handleRemember)

    And three combinators build the rest:

    moderation := hermes.All(
    hermes.GroupChat,
    hermes.PhotoMessage,
    hermes.Not(hermes.FromUsers(bannedIDs...)),
)
bot.On(moderation, moderateGroupPhoto)

    All is AND, Any is OR, Not is negation. Set-based filters like FromUsers pre-build a map at registration, so the per-update check is constant time no matter how long the list. Writing your own filter is one function. There's nothing to subclass: 

    func weekdaysOnly(c *hermes.Context) bool {
    day := time.Now().Weekday()
    return day != time.Saturday && day != time.Sunday
}

    Groups share filters

    An admin section is the textbook case: 

    admin := bot.Group(hermes.FromUsers(adminIDs...))

admin.Command("ban", handleBan)
admin.Command("stats", handleStats)
admin.On(hermes.TextPrefix("/broadcast "), handleBroadcast)

    Every route on the group carries the group's filters. The alternative (repeating FromUsers(adminIDs...) on every route) is how an id gets added in nine places and missed in the tenth.

    Middleware, in declaration order

    bot.Use(
    hermes.Recover(),                  // outermost: panics become errors
    hermes.Timeout(15 * time.Second),  // then: every handler gets a deadline
    metrics,                           // then: your own
)

    Middleware declared first runs first; it is the outermost wrapper. The two you should install on every bot, always:

    • Recover() converts a handler panic into a *hermes.PanicError with the stack trace attached. Without it a panic in one handler is contained by the dispatcher but you learn nothing; with it, your error handler sees everything.
    • Timeout(d) derives a per-update deadline and passes a cloned context down the chain. It is the difference between "a slow handler" and "a slow handler that eventually gives up".

    Writing middleware that doesn't lie

    Middleware is func(Handler) Handler. A logging middleware is five lines: 

    func logUpdates(next hermes.Handler) hermes.Handler {
    return func(c *hermes.Context) error {
        start := time.Now()
        err := next(c)
        log.Printf("update=%d type=%s took=%s err=%v",
            c.Update.ID, c.Type(), time.Since(start).Round(time.Millisecond), err)
        return err
    }
}

    Three rules keep middleware honest:

    • Always return next(c)'s error, wrapped or verbatim. Swallowing it makes failures invisible to the error handler and to anyone debugging.
    • Decide explicitly to skip. If the middleware sometimes doesn't call next (rate limiting, auth), make that the loud path: return an error or answer the user; don't just return nil.
    • Mutate the context through the documented surface. Timeout works by cloning the context and swapping its Context field; if you need the same trick, c.Clone() exists for exactly this.
    The fallback is your safety net

    bot.OnUpdate catches everything no route claimed. Two good uses: replying "sorry, I don't know that command" in private chats, and counting unmatched updates in metrics — a rising count usually means clients are sending stale buttons after a deploy.
