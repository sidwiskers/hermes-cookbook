    Chapter 5

    Typed callbacks

    Callback data is a string, but your intent isn't. Hermes's CallbackCodec turns "parse the string, hope for the best" into "decode a typed value, or reject the tap cleanly".

    The problem with raw strings

    Every callback handler in every bot framework starts the same way: 

    // The old way. We've all written it.
parts := strings.Split(c.Data(), ":")
if len(parts) != 3 || parts[0] != "order" {
    return c.Answer("Hmm, that button is stale.")
}
id, err := strconv.ParseInt(parts[1], 10, 64)
if err != nil { /* … */ }
action := parts[2] // "approve"? "refund"? "apprve"? who knows

    It works until someone renames a prefix in one place and not the other, or a user replays a year-old button from a cached client. Typed callbacks move all of that into one codec defined once, next to the button that produces the data.

    Codecs for the common shapes

    var userPick = hermes.StringCallback("user:")   // payload is a raw string
var pageNav  = hermes.IntCallback("page:")        // payload is an int
var orderAct = hermes.Int64Callback("order:")     // payload is an int64

    A codec does both directions. Building the button encodes; handling the tap decodes: 

    // Building the keyboard:
keyboard := hermes.Keyboard(
    hermes.Row(
        pageNav.MustButton("← Prev", page-1),
        pageNav.MustButton("Next →", page+1),
    ),
)

// Handling the tap:
bot.CallbackPrefix("page:", pageNav.Handler(func(c *hermes.Context, page int) error {
    return c.Edit(renderPage(page))   // page is already an int
}))

    MustButton panics if the encoded value would exceed Telegram's 64-byte limit — which is what you want for static configuration, because it fails at startup, loudly, instead of at 2 a.m. in production. For user-influenced values use Button and handle the error yourself.

    Structured payloads with JSON

    When two or three fields travel together, there's JSONCallback: 

    type moderation struct {
    PostID int64  `json:"p"`
    Action string `json:"a"` // "approve" | "reject"
}

var mod = hermes.JSONCallback[moderation]("mod:")

// produce:
btn, err := mod.Button("Approve", moderation{PostID: 42, Action: "approve"})

// consume:
bot.CallbackPrefix("mod:", mod.Handler(func(c *hermes.Context, m moderation) error {
    if m.Action != "approve" && m.Action != "reject" {
        return c.Answer("Unknown action.")
    }
    return applyModeration(c, m)
}))

    Short JSON tags are not paranoia — they are how a two-field struct stays inside 64 bytes. If a payload starts growing, that's the framework nudging you toward storing state server-side and shipping only an id, which was the right design anyway.

    When the codec rejects

    Parse (and therefore Handler) rejects two things: wrong prefix, and malformed payload. Both happen in the wild: stale messages, replayed taps, clients with cached keyboards from three releases ago. The handler path surfaces the decode failure as an ordinary error through your error handler; the tap gets no answer unless you send one. If you want the user told, wrap it: 

    bot.CallbackPrefix("mod:", func(c *hermes.Context) error {
    m, err := mod.Parse(c.Data())
    if err != nil {
        return c.Answer("That button is from an older version.")
    }
    return applyModeration(c, m)
})

    That one toast, "that button is from an older version", will save you more confused bug reports than any other line in this chapter.

    Prefix discipline

    A few rules that keep a growing bot sane:

    • One codec owns one prefix, and the prefix ends in a separator: "user:", not "user". Otherwise "user:42" and "username:bob" collide in ways you will debug at midnight.
    • Define codecs at package scope, next to the handlers that use them. The codec is the protocol documentation.
    • Never put secrets in callback data. It's visible to the client, logged by proxies, and replayable by construction. Ids and intent, nothing else.
